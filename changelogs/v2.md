# Changelog - v2

All notable changes to `ts-mailkit` in version 2.x are documented here.

---

## [2.1.0] - 2026-10-29

### Added

- **Bulk messaging API**: new `MailKit` methods backed by the Zoho CPaaS batch endpoints (no client-side loops):
  - `sendBulkMail(options)` — sends a single in-built template DTO to many recipients; the provider delivers an individual copy to each recipient (`POST /v1.1/email/batch`).
  - `sendKnownTemplate(options)` — sends a single email using a provider-side template ID (`POST /v1.1/email/template`).
  - `sendBulkKnownTemplate(options)` — sends a batch using a provider-side template ID with per-recipient `mergeInfo` (`POST /v1.1/email/template/batch`).
- **Template build utilities**: `buildHTMLTemplate(dto, options?)` and `buildPlainTextTemplate(dto)` produce upload-ready template content from the canonical `EmailTemplateDto`.
- **Zoho CPaaS response types**: `CpaasResponseItem`, `CpaasSuccessResponse`, `CpaasErrorData`, `CpaasErrorResponse` are exported so consumers can type-check `SendResult.rawResponse`.
- **`CpaasHttpConfig.preferTemplateAlias`**: when `true`, template sends use `template_alias` instead of `template_key`.

### Changed

- **ZeptoMail renamed to Zoho CPaaS**: `ZeptoMailHttpSender` → `CpaasHttpSender`, `ZeptoMailHttpConfig` → `CpaasHttpConfig`, `ZeptoMailSendPayload` → `CpaasSendPayload`. The default API host is now `cpaas.zoho.com`.
- **`SendResult.rawResponse`**: the raw provider response is now exposed as `rawResponse` (the previous `response` field is kept as a deprecated alias).
- **Unified transport interface**: `IEmailSender` gains optional `sendBulk`, `sendKnownTemplate`, and `sendBulkKnownTemplate` capabilities. `MailKit` throws `ConfigurationError` when a transport lacks a required capability.

### Deprecated

- `MailKit.send()` — use `MailKit.sendMail()` instead.
- `SendResult.response` — use `SendResult.rawResponse` instead.
- `ZeptoMailHttpSender`, `ZeptoMailHttpConfig`, `ZeptoMailSendPayload`, `ZeptoMailAddressObject`, `ZeptoMailRecipientWrapper`, `ZeptoMailAttachmentPayload` — use the `Cpaas*` equivalents. The `src/transports/zeptomail/` path remains as a re-export shim.

### Migration Guide from 2.0.x

```ts
// Before
await mailer.send({ to: "user@example.com", template: dto });
const raw = result.response;
import { ZeptoMailHttpSender } from "ts-mailkit";

// After
await mailer.sendMail({ to: "user@example.com", template: dto });
const raw = result.rawResponse;
import { CpaasHttpSender } from "ts-mailkit";
```

## [2.0.1] - 2026-09-22

### Fixed

- **ZeptoMailHttpSender fetch binding on strict runtimes**:
  - `ZeptoMailHttpSender` now binds `fetch` to `globalThis` to prevent "Illegal invocation" errors on strict-`this` runtimes (undici, Cloudflare Workers `workerd`). On Node < 18 without a global `fetch`, a helpful error message guides users to pass a custom `fetch` via `ZeptoMailHttpConfig`.

---

## [2.0.0] - 2026-09-20

### Breaking Changes

- **Removed `*_Legacy` positional factory methods**:
  - Removed `createEmailVerification_Legacy`, `createPasswordReset_Legacy`, `createSimpleMessage_Legacy`, `createNewsLetter_Legacy`, `create2FAEmail_Legacy`, `createMagicLinkEmail_Legacy` (instance + static).
  - Factory methods accept only Parameter Objects backed by canonical DTO types (`EmailVerificationParams`, `PasswordResetParams`, `SimpleMessageParams`, `NewsletterParams`, `TwoFactorParams`, `MagicLinkParams`).

### Migration Guide from 1.x

Replace positional calls with parameter objects:

```ts
// Before (1.x legacy)
EmailTemplateFactory.createEmailVerification_Legacy("Alex", url, "123456", "Acme");

// After (2.0.0)
EmailTemplateFactory.createEmailVerification({
  username: "Alex",
  verificationUrl: url,
  otp: "123456",
  brandName: "Acme",
});
```
